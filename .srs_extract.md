# 1. Introduction

## 1.1 Purpose

This Software Requirements Specification defines the functional,
technical, AI, data, security, operational and evaluation requirements
for LEDGERFLOW, an autonomous revenue recovery operating system designed
for Razorpay merchants. It is intended to serve as the single
engineering baseline for implementation, testing, demo preparation and
judging.

## 1.2 Problem Statement

Revenue leakage rarely appears as one isolated failure. A customer may
encounter a payment failure, abandon checkout, fail a recurring charge,
miss an invoice due date or stop responding to a promise to pay.
LEDGERFLOW addresses the operational gap between detecting those events
and actually recovering the money.

## 1.3 Buildathon Alignment

Track 03 requires an agent that detects revenue at risk, determines the
appropriate intervention and executes a bounded recovery workflow. The
explicit bar is measured money recovered across a batch, compliant
escalation, stopping rules and an audit trail. \[R1\]

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Design principle** Every AI decision that can affect money must produce a structured recommendation, pass deterministic policy checks, execute through an approved action service, and remain auditable.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

# 2. Product Overview

## 2.1 Product Name

LEDGERFLOW --- Autonomous Revenue Recovery Operating System

## 2.2 Value Proposition

-   Detect recoverable revenue instead of treating every failed payment
    equally.

-   Diagnose the likely cause using payment state, customer history,
    transaction context and prior interventions.

-   Choose the intervention with the highest expected recovery value
    subject to merchant policies.

-   Execute bounded actions through Razorpay test-mode APIs and track
    the result.

-   Learn from intervention outcomes so future recommendations become
    more evidence-based.

-   Expose why an action was proposed, which controls approved it, what
    happened afterward and when the agent stopped.

## 2.3 Core Product Loop

Event / Record → Detect → Diagnose → Prioritize → Plan Intervention →
Policy Check → Execute → Verify → Recover / Escalate → Learn

## 2.4 Primary User

Merchant operations, finance-ops or revenue-ops user who needs to
identify at-risk revenue and approve, monitor or audit recovery actions.

## 2.5 Operating Modes

  **Mode**          **Purpose**                                                                           **External money impact**
  ----------------- ------------------------------------------------------------------------------------- ------------------------------------------------
  Live Test Mode    Real Razorpay test-mode resources and webhooks for end-to-end integration.            No live customer funds; test environment only.
  Simulation Mode   Synthetic 100--200 case benchmark used to compare policies and recovery strategies.   None; all financial outcomes are simulated.
  Review Mode       Human-in-the-loop mode for high-value, low-confidence or policy-sensitive cases.      Only after explicit approval within test mode.

# 3. Goals and Success Criteria

## 3.1 Product Goals

1.  Identify meaningful revenue-at-risk opportunities with enough
    evidence for action.

2.  Improve recovery outcome versus a static baseline such as
    retry-everything or remind-everything.

3.  Automate low-risk actions while escalating high-risk or high-value
    decisions.

4.  Provide an audit trail sufficient to reconstruct every autonomous
    decision.

5.  Demonstrate recovery performance on a reproducible synthetic batch
    and a real Razorpay test-mode workflow.

## 3.2 Hackathon Success Metrics

  **Metric**                   **Definition**                                                                                             **Target for prototype**
  ---------------------------- ---------------------------------------------------------------------------------------------------------- ------------------------------------------------------------------------------------------------------------
  Revenue at Risk Identified   Sum of monetary value of cases classified as recoverable or potentially recoverable.                       100% of benchmark cases have an outcome label; \>=90% event ingestion completeness.
  Recovery Rate                Recovered amount / eligible at-risk amount.                                                                Beat static baseline by \>=10% in benchmark scenario; actual target to be tuned after dataset calibration.
  Intervention Accuracy        Cases where selected intervention matches benchmark-best action or falls within approved equivalent set.   \>=75% on held-out benchmark.
  Policy Violation Rate        Autonomous actions that bypass a mandatory policy.                                                         0%.

  Escalation Reliability       Cases meeting escalation rules that reach approval queue rather than automatic execution.                  100% in test cases.

# 5. Scope

## 5.1 In Scope

-   Payment-failure recovery as the deepest primary workflow.

-   Checkout abandonment recovery as a secondary workflow using a
    controlled demo checkout and payment-link action.

-   B2B invoice / receivable recovery as a secondary workflow.

-   Failed-subscription recovery as an optional extension, not the sole
    product differentiator.

-   Four cooperating agents: Detection, Diagnosis, Intervention Planner,
    Action Executor.

-   Deterministic policy engine, stopping rules, escalation queue and
    approval workflow.

-   Razorpay test-mode API integration, webhooks, signature validation
    and idempotent event processing.

-   Synthetic benchmark generator and baseline comparison.

-   Case-centric dashboard, analytics, audit trail and simulation lab.

## 5.2 Out of Scope for MVP

-   Live-mode monetary transactions.

-   Autonomous refunds, disputes or other destructive financial actions.

-   Full accounting / ERP replacement.

-   Production-grade omnichannel messaging infrastructure.

-   Custom foundation model training.

-   Large-scale distributed orchestration or Kubernetes deployment.

-   Voice recovery as a core path; it may be added as a demo extension
    if time permits.

# 7. Four-Agent Architecture

LEDGERFLOW uses four agents with narrow responsibilities. The agents do
not form a free-form swarm. They communicate through typed contracts,
while deterministic services control money-related side effects.

![](media/image1.png){width="6.65in" height="3.879166666666667in"}

## Agent 1 --- Detection Agent

Find revenue-at-risk opportunities and estimate whether the case merits
intervention.

  **Aspect**        **Specification**
  ----------------- -----------------------------------------------------------------------------------------------------------
  Inputs            Normalized event, transaction amount/status, customer history, workflow context, merchant policy summary.
  Outputs           is_at_risk, risk_score, revenue_at_risk, urgency, reason_codes, evidence_refs.
  Permitted tools   Read-only database queries; risk feature service.
  Hard guardrails   Cannot execute actions; cannot modify financial records.

## Agent 2 --- Diagnosis Agent

Explain why the revenue is at risk and identify the most likely recovery
context.

  **Aspect**        **Specification**
  ----------------- ----------------------------------------------------------------------------------------
  Inputs            Case, payment status, failure reason, customer history, prior interventions, timing.
  Outputs           root_cause, confidence, evidence, uncertainty_flags, recommended_diagnostic_next_step.
  Permitted tools   Read-only data and optional retrieval of merchant playbooks.
  Hard guardrails   Must allow UNKNOWN; cannot invent missing payment facts.

## Agent 3 --- Intervention Planner

Choose the best bounded intervention using expected recovery value and
policy context.

  **Aspect**        **Specification**
  ----------------- -----------------------------------------------------------------------------------------------------------------
  Inputs            Risk score, diagnosis, history, prior actions, action catalog, policy summary, strategy-performance statistics.
  Outputs           recommended_action, recovery_probability, expected_recovery, reason_codes, alternatives, stop_condition.
  Permitted tools   Read-only policy snapshot; strategy analytics.
  Hard guardrails   May only choose allow-listed actions; cannot bypass policy or call Razorpay.

## Agent 4 --- Action Executor

Turn an approved structured action into a verified external operation.

  **Aspect**        **Specification**
  ----------------- ----------------------------------------------------------------------------------------
  Inputs            Approved action, case ID, policy decision, idempotency key, Razorpay resource IDs.
  Outputs           execution_status, external_resource_id, next_state, error_code, verification_required.
  Permitted tools   Razorpay API client; webhook registry; notification adapter.
  Hard guardrails   No generative decisions; deterministic validation; strict idempotency; hard stops.

## 7.5 Supporting Deterministic Services

-   Policy Engine --- evaluates money-related rules and returns PASS,
    BLOCK or ESCALATE.

-   Verification Service --- reconciles external state with internal
    action records.

-   Event Processor --- signature validation, normalization, ordering
    and deduplication.

-   Strategy Analytics --- aggregates intervention outcomes and computes
    effectiveness.

-   Audit Service --- writes decision, policy, execution and outcome
    events to the audit log.

# 9. Revenue-Risk Scoring

## 9.1 Risk Score

The risk score estimates how strongly a transaction or receivable merits
attention. It is not itself permission to act.

risk_score = 0.30 \* failure_severity\
+ 0.20 \* customer_intent\
+ 0.20 \* payment_reliability\
+ 0.15 \* amount_score\
+ 0.10 \* time_sensitivity\
+ 0.05 \* recovery_window\
\
All components normalized to \[0, 1\].

## 9.2 Expected Recoverable Revenue

Expected recoverable revenue (ERR) is the key prioritization signal for
the intervention queue.

ERR = revenue_at_risk × recovery_probability × intervention_feasibility

The final score must be deterministic once model probabilities and
policy feasibility are supplied. The system shall not present a model
probability as a guarantee of recovery.

## 9.3 Customer Segmentation

  **Segment**             **Typical behavior**                      **Default action posture**
  ----------------------- ----------------------------------------- ------------------------------------------------------------------
  New customer            Little history; uncertain intent.         Prefer low-friction, low-contact recovery; escalate uncertainty.
  Repeat customer         Established successful payment history.   Higher confidence in contextual recovery.
  High-value customer     Large amount or high lifetime value.      Tighter limits and more human review.
  B2B customer            Invoice / receivable context.             Reminder, promise-to-pay and escalation flow.
  Subscription customer   Recurring billing context.                Retry / payment-link / reminder within defined cadence.

# 10. Policy, Guardrails and Human Approval

## 10.1 Example Policy Object

{\
\"max_retry_count\": 2,\
\"max_automated_amount\": 500000,\
\"min_action_confidence\": 0.70,\
\"cooldown_minutes\": 30,\
\"max_actions_per_customer_per_day\": 3,\
\"require_human_approval_above\": 100000\
}

## 10.2 Policy Decision States

  **State**   **Meaning**                                           **Action**
  ----------- ----------------------------------------------------- ------------------------------------------------
  PASS        Action satisfies all configured rules.                Executor may run.
  BLOCK       Action violates a hard rule or lacks required data.   Do not execute; log reason.
  ESCALATE    Action may be valid but requires human approval.      Add to approval queue; no external action yet.

## 10.3 Mandatory Stopping Rules

-   Stop after maximum retry / reminder count.

-   Stop when customer has already completed the recovery or payment.

-   Stop after a policy-defined daily action limit.

-   Stop when action confidence is below the autonomous threshold.

-   Stop after repeated API failure beyond retry budget.

-   Stop when event state indicates conflicting or unknown external
    status.

-   Stop when the action would exceed the autonomous monetary threshold.

## 10.4 Human Approval Queue

The queue shall show case value, diagnosis, proposed action, confidence,
expected recovery, policy checks, and prior actions. Approval and
rejection must be explicit and auditable.

# 11. Recovery Workflows

## 11.1 Workflow A --- Payment Failure Recovery (Primary)

Payment failure event\
→ Detection Agent\
→ Create risk case\
→ Diagnosis Agent\
→ Intervention Planner\
→ Policy Engine\
PASS → Action Executor → Razorpay action → Webhook/API verification\
ESCALATE → Approval Queue → Executor after approval\
BLOCK → Case closed with reason\
→ Outcome recorded → Recovery metrics updated

## 11.2 Workflow B --- Checkout Abandonment Recovery

Checkout started\
→ cart / amount / intent events\
→ inactivity threshold reached\
→ Detection Agent\
→ Diagnosis Agent\
→ Planner chooses payment_link / no_action\
→ Policy Engine\
→ create + optionally notify payment link\
→ payment_link.paid / payment verification\
→ recovery outcome

LEDGERFLOW shall use a controlled demonstration checkout for this
workflow. Abandonment events should be generated by the project frontend
rather than inferred from nonexistent Razorpay events.

## 11.3 Workflow C --- B2B Receivable / Invoice Recovery

Invoice issued\
→ due date passes / invoice state changes\
→ Detection\
→ Diagnosis\
→ Planner: reminder / promise-to-pay / escalate\
→ Policy Engine\
→ Invoice notification / operator task\
→ monitor payment / response\
→ close or escalate

## 11.4 Workflow D --- Failed Subscription Recovery

Subscription-related billing event\
→ Detection\
→ Diagnosis\
→ Planner: retry / payment link / reminder / escalate\
→ Policy\
→ Executor\
→ webhook / API verification\
→ close or continue within action budget

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Scope note** Subscription recovery is intentionally one workflow within LEDGERFLOW, not the entire product. The differentiation is the unified decision engine spanning multiple revenue-leak scenarios.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

# 12. Razorpay Integration Requirements

## 12.1 API and Environment

Razorpay exposes REST APIs, provides Test and Live API keys, and
documents \`https://api.razorpay.com/v1\` as the gateway base for most
APIs. \[R2\]

## 12.2 Payments

The Payments APIs support retrieval of payment details and payment
status operations such as capture. LEDGERFLOW shall use payment data
primarily for observation, diagnosis and verification; it shall not
pretend that the Payments API itself is a generic payment-collection
endpoint. \[R3\]

## 12.3 Payment Links

Payment Links are a key recovery action. Razorpay documents APIs to
create, fetch, update, cancel and resend notifications for Payment
Links, and supports webhook events such as \`payment_link.paid\`.
\[R4\]\[R5\]

## 12.4 Invoices

Razorpay Invoices APIs support creating, issuing, fetching, sending,
updating and cancelling invoices. These operations can underpin the B2B
receivable recovery workflow. \[R6\]

## 12.5 Subscriptions

Razorpay documents APIs for plans, subscriptions, subscription links,
subscription fetching, pause/resume and cancellation. Test-mode limits
or environment constraints shall be verified during implementation.
\[R7\]

## 12.6 Webhooks

Webhook processing shall validate the \`X-Razorpay-Signature\` using the
raw request body and configured webhook secret. The integration shall
account for event idempotency and event ordering. Razorpay explicitly
documents test-mode webhook testing and signature validation with
HMAC-SHA256. \[R8\]

## 12.7 Integration Matrix

  **Capability**          **Use in LEDGERFLOW**          **Primary API / event**                **Test required**
  ----------------------- ------------------------------ -------------------------------------- -----------------------------------------------
  Payment observation     Detect + verify                Payments APIs                          Fetch, status, edge states
  Payment Link recovery   Execute recovery               Payment Links API; payment_link.paid   Create, pay, verify, duplicate request
  Invoice recovery        Receivable workflow            Invoices API + invoice events          Create, issue, send, verify payment
  Subscription workflow   Recurring recovery extension   Subscriptions API                      Create link/subscribe, billing event handling
  Webhooks                Event-driven state changes     Webhook endpoint                       Signature, duplicate, out-of-order, retry
  API reconciliation      Backfill and verify            REST APIs                              Pagination, timeout, rate/error handling

  -------------------- -------------------------------------------------------- ---------------------------------------------------------------

## 13.2 Architectural Constraints

-   No direct Razorpay secret exposure to the browser or LLM.

-   No free-form LLM tool calling against money-moving endpoints.

-   Every side effect must be linked to a case and idempotency key.

-   Every autonomous action must be reconstructable from database
    records.

-   Simulation mode must never reach external Razorpay endpoints.

## 14.2 Case State Machine

NEW → ANALYZING → DIAGNOSED → PLANNED → POLICY_REVIEW\
\
POLICY_REVIEW → APPROVED → EXECUTING → VERIFYING → RECOVERED\
POLICY_REVIEW → ESCALATED → WAITING_HUMAN → APPROVED / REJECTED\
POLICY_REVIEW → BLOCKED\
VERIFYING → FAILED → RETRYING / ESCALATED / CLOSED\
ANY STATE → CLOSED when payment is complete or stopping rule is reached

# 19. Security and Privacy

## 19.1 Secrets

-   Razorpay key secret remains server-side only.

-   Gemini API key remains server-side only.

-   Webhook secret remains server-side only.

-   Development secrets supplied through environment variables / secret
    manager.

## 19.2 AI Safety

-   LLM outputs are treated as untrusted recommendations.

-   No direct tool access from model to money-moving endpoints.

-   All actions use allow-listed enums.

-   All amounts are derived from trusted database/API data rather than
    generated text.

-   High-value or uncertain cases use human approval.

-   Unknown / no-action outcomes are first-class states.

## 19.3 Webhook Security

The webhook endpoint shall validate the signature against the raw
request body using the configured secret before parsing and acting on
the event. \[R8\]

## 19.4 Data Minimization

The system should store only the payment and customer information
necessary for recovery logic and audit. Sensitive payment instrument
details shall not be copied into the application database unless
explicitly required by an approved API use case.

# 20. Reliability and Failure Handling

## 20.1 Duplicate Events

Incoming webhook event IDs and action idempotency keys must prevent
duplicate external side effects.

## 20.2 Lost Response

If the external action may have succeeded but the response is ambiguous,
LEDGERFLOW shall not immediately create another action. It shall
reconcile external state first, then continue or escalate.

## 20.3 External API Errors

  **Failure**            **Expected behavior**
  ---------------------- -----------------------------------------------------------------------------------
  Timeout                Retry once using same idempotency key if safe; then verify before retrying again.
  4xx validation error   Do not retry blindly; record error and escalate / close.
  5xx transient error    Bounded retry with backoff; stop after retry budget.
  Webhook delayed        Case remains VERIFYING; poll/reconcile only according to policy.
  Out-of-order event     Use entity timestamps/state checks; ignore stale state transitions.
  Conflicting state      Mark UNKNOWN, prevent action, escalate for review.

## 20.4 Graceful Agent Failure

If any AI agent times out, returns invalid JSON or produces
low-confidence output, the system must not fail open. It shall switch to
a safe state: deterministic fallback, NO_ACTION or ESCALATE depending on
workflow.

# 29. Glossary

  **Term**                       **Definition**
  ------------------------------ --------------------------------------------------------------------------------------------
  Revenue at Risk                Monetary value associated with an event where recovery may still be possible.
  Expected Recoverable Revenue   Revenue at risk multiplied by estimated recovery probability and intervention feasibility.
  Recovery Case                  The tracked unit of work containing diagnosis, decision, policy, action and outcome.
  Intervention                   A bounded action intended to recover revenue, such as a retry, payment link or reminder.
  Stopping Rule                  A deterministic rule that tells the agent to stop acting.
  Escalation                     Transfer of a case to a human reviewer rather than autonomous execution.
  Action Executor                The fourth agent / deterministic integration layer responsible for approved side effects.
  Simulation Mode                An isolated execution path using synthetic data and no external money-moving calls.
  Audit Trail                    Append-oriented record of relevant decisions, policy checks, actions and outcomes.
  Held-out Set                   Benchmark cases not used when tuning prompts or heuristics.
